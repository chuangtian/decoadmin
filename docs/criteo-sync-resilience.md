# Criteo 同步故障处理

本地实现，不代表已发布到服务器。仅改变后台读取广告报表时的失败处理，不修改广告、店铺数据或授权。

- 将 HTTP 状态及重试时间保存为脱敏结构，不保存响应正文或异常中的凭据。
- Criteo 的 429、408、5xx 与连接错误进入持久化冷却：30 分钟、1 小时、2 小时、4 小时，常规上限 6 小时；若 `Retry-After` 要求更久则尊重它（保护性上限 7 天）。支持秒数和 HTTP 日期。
- 小时调度和同步入口均检查冷却，期间不执行实际 API 请求。暂时性失败不再叠加队列的 120/600 秒短重试；冷却结束后由下一轮小时调度继续。因此实际重试可能晚于冷却截止时间。
- 按组织、店铺和渠道隔离；凭据版本变化可重新尝试。暂停中的优先同步和历史回填会恢复原模式、原报表日期窗口。
- Criteo 暂时性失败首次出现后的 1 小时内不生成飞书告警，持续失败才告警。401/403 授权问题仍及时告警。
- 广告告警使用渠道名称和明确原因，不再笼统叫“Shopify 数据同步失败”。同一同步任务只产生一条失败告警，不因 429/504 错误码变化或计数增加重复通知。
- 成功后对应旧告警自动解决；仍待发送的该任务告警跳过。已发出的消息不会撤回。恢复后的新任务再次失败属于新事件。
- 未改变其他渠道的队列重试时序，没有关闭任何店铺的通知设置。

测试使用本地隔离数据库、HTTP 模拟与队列模拟，不请求真实 Criteo 或飞书。

参考：[Criteo Marketing Solutions 限流及指数退避建议](https://developers.criteo.com/marketing-solutions/docs/rate-limits)。当前较长等待时间是针对后台小时报表、持续 429/504 的应用策略，并非 Criteo 强制要求的固定时长。
